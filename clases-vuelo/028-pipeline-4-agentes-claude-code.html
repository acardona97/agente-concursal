Pipeline de 4 Agentes con Claude Code

Planner, Coder, Tester y Reviewer encadenados para entregar una feature mientras duermes.

Introduccion

Cuatro agentes IA pueden enviar una feature mientras duermes. La mayoria de personas nunca los conecta correctamente. Los activan uno por uno, a mano, cada uno olvidando lo que hizo el anterior. Tu sigues siendo el cuello de botella.

El problema no es la capacidad de los agentes. Es la arquitectura. Un agente manejando todo el pipeline de desarrollo — planear, codificar, probar y revisar — llena su ventana de contexto tan rapido que la calidad cae a la mitad del proceso.

Un solo agente haciendo todo

  • Contexto se llena mezclando planeacion, codigo, pruebas y notas de revision
  • Calidad cae progresivamente
  • Cada sesion empieza desde cero
  • Tu sigues siendo el puente entre etapas

Cuatro especialistas en pipeline

  • Cada agente tiene contexto limpio y estrecho
  • Calidad consistente en cada etapa
  • Handoffs automaticos via archivos compartidos
  • Un trigger, cuatro etapas, una feature terminada

Por que un Pipeline Gana a una Pila de Agentes

El truco que convierte cuatro agentes separados en un pipeline cohesionado es el archivo de handoff. Cada agente escribe su output en un archivo predecible donde el siguiente puede leerlo.

Planner
spec.md
→
Coder
changes.md
→
Tester
test-results.md
→
Reviewer
review.md
Agente Lee Escribe Modelo
Planner La peticion de feature + codebase .pipeline/spec.md Opus
Coder .pipeline/spec.md .pipeline/changes.md Sonnet
Tester .pipeline/changes.md + spec .pipeline/test-results.md Sonnet
Reviewer Todo lo anterior + git diff .pipeline/review.md Opus

El orquestador que los ejecuta en orden es un solo slash command. Cuatro subagentes, un comando, una carpeta compartida para handoffs.

Agente 1: The Planner

PLANNER · OPUS · SUBAGENTE

El que convierte vagedad en precision

El Planner nunca escribe codigo. Su trabajo es convertir una peticion de feature vaga en una spec concreta que el Coder puede seguir sin adivinar. Una spec vaga produce codigo vago sin importar que tan bueno sea el Coder — por eso esta etapa se ejecuta con Opus. Establece el techo de calidad para todo lo que viene despues.

Crea el archivo .claude/agents/planner.md:

---
name: planner
description: Turns a feature request into an implementation spec. Use as the second subagent in the pipeline, after requirements are clear.
tools: Read, Grep, Glob, Write
model: opus
---

You are a planning specialist. You do NOT write implementation code.

Given a feature request:
1. Read the relevant parts of the codebase to understand current patterns
2. Write a spec to `.pipeline/spec.md` containing:
   - Files to create or modify, with exact paths
   - The interface or function signatures needed
   - Edge cases the implementation must handle
   - Which existing patterns to follow (name the file to copy from)
3. Flag anything ambiguous as an OPEN QUESTION at the top of the spec.

Keep the spec tight, so leave no gaps and invent no requirements that weren't asked for.

Por que Opus para el Planner?

La planeacion requiere razonamiento profundo sobre el codebase y la peticion. Opus tiene la capacidad de identificar patrones sutiles, anticipar edge cases no obvios y escribir specs que eliminan la ambiguedad. El costo adicional de Opus en esta etapa se recupera en el tiempo que el Coder no pierde en suposiciones incorrectas.

Que debe contener spec.md

Una buena spec del Planner tiene esta estructura:

# Feature Spec: [nombre de la feature]

## OPEN QUESTIONS (si las hay)
- Pregunta 1: [que no queda claro de la peticion]

## Files to Modify
- `src/auth/login.py` — agregar rate limiting middleware
- `tests/test_auth.py` — agregar casos de prueba para rate limiting

## Interfaces Required
```python
def apply_rate_limit(endpoint: str, user_id: str, max_attempts: int = 5) -> bool:
    """Returns True if request is allowed, False if rate limited."""
```

## Edge Cases to Handle
- Usuario sin autenticar (usar IP como identificador)
- Rate limit diferente para admin vs usuario normal
- Reset del contador despues de autenticacion exitosa

## Patterns to Follow
- Sigue el patron de middleware en `src/middleware/auth_middleware.py`
- Usa el mismo logging pattern que `src/auth/logout.py`

Agente 2: The Coder

CODER · SONNET · SUBAGENTE

El que implementa la spec, sin desviarse

El Coder lee la spec y escribe la implementacion. No planea y no revisa su propio trabajo. Solo construye exactamente lo que dice la spec. Sonnet es la eleccion correcta aqui: implementacion contra una spec clara es el trabajo costo-calidad equilibrado que Sonnet maneja mejor.

Crea el archivo .claude/agents/coder.md:

---
name: coder
description: Implements the spec at .pipeline/spec.md. Use as the second subagent in the ship pipeline.
tools: Read, Write, Edit, Grep, Glob, Bash
model: sonnet
---

You are an implementation specialist.

1. Read `.pipeline/spec.md` in full. If it has OPEN QUESTIONS, stop and surface them instead of guessing.
2. Implement exactly what the spec describes. Follow the patterns it names. Do not add features it didn't ask for.
3. Write a short summary to `.pipeline/changes.md`: which files changed, what each change does, and anything the Tester should focus on.

You write code that matches the repo. You do not refactor unrelated code or "improve" things outside the spec's scope.

El archivo changes.md

El handoff del Coder al Tester no es implicito. changes.md es el mapa que le dice al Tester exactamente donde mirar:

# Changes Summary

## Files Modified
- `src/auth/login.py` — Added `apply_rate_limit()` function and middleware decorator
- `src/middleware/rate_limit.py` — New file with RateLimitStore class
- `config/settings.py` — Added RATE_LIMIT_MAX_ATTEMPTS and RATE_LIMIT_WINDOW_SECONDS

## What Changed
Login endpoint now checks rate limit before processing credentials.
Rate limiting uses in-memory store with TTL. Resets on successful auth.

## Tester Focus Areas
- Test that 5 failed attempts within 60s triggers rate limit
- Test that successful auth resets the counter
- Test IP-based limiting for unauthenticated requests
- Test that admin users have higher limit (10 attempts)

La diferencia entre probar a ciegas y probar con precision es este archivo.

Agente 3: The Tester

TESTER · SONNET · SUBAGENTE

El que verifica comportamiento, no implementacion

El Tester lee lo que cambio y escribe pruebas que demuestran que la feature funciona. Luego las ejecuta. Si fallan, para. No arregla el codigo el mismo — eso seria mezclar roles y contaminar la separacion de responsabilidades del pipeline.

Crea el archivo .claude/agents/tester.md:

---
name: tester
description: Writes and runs tests for changes described in .pipeline/changes.md.
tools: Read, Write, Edit, Grep, Glob, Bash
model: sonnet
---

You are a test specialist.

1. Read `.pipeline/changes.md` to see what was built and where.
2. Read the changed files and the spec at `.pipeline/spec.md`.
3. Write tests covering: the happy path, the edge cases the spec named, and at least one failure case. Match the repo's test framework.
4. Run the tests. If any fail, write the failures to `.pipeline/test-results.md` and STOP. Do not fix the code yourself.
5. If all pass, note that in `.pipeline/test-results.md`.

You test behavior, not implementation details. A failing test means the pipeline pauses for the Reviewer, not that you patch around it.

Por que el Tester no arregla el codigo?

Si el Tester encuentra un fallo y lo arregla el mismo, suceden dos cosas malas:

  1. El Coder nunca sabe que su implementacion tenia un bug — no aprende
  2. El arreglo del Tester puede ser incorrecto o inconsistente con los patrones del codebase

La regla es: test falla, pipeline se detiene, humano (tu) decides si reiniciar desde el Coder o arreglarlo directamente. El pipeline es un gate, no un auto-corrector.

Estructura de test-results.md segun el resultado

# Test Results

## Status: ALL PASS

## Tests Run
- test_rate_limit_triggers_after_5_attempts: PASS
- test_successful_auth_resets_counter: PASS
- test_ip_limiting_unauthenticated: PASS
- test_admin_higher_limit: PASS
- test_rate_limit_resets_after_window: PASS

## Coverage
Modified files: 94%
New file src/middleware/rate_limit.py: 87%
# Test Results

## Status: FAILURES FOUND

## Failing Tests
- test_admin_higher_limit: FAIL
  AssertionError: Expected 10 attempts for admin, got 5
  The admin check in apply_rate_limit() uses the wrong user role field.

## Passing Tests
- test_rate_limit_triggers_after_5_attempts: PASS
- test_successful_auth_resets_counter: PASS

## Note for Reviewer
Pipeline paused. Admin role check needs fix in src/auth/login.py line 47.

Agente 4: The Reviewer

REVIEWER · OPUS · SUBAGENTE · SOLO LECTURA

El ultimo gate antes de que toques el codigo

El Reviewer lee todo lo que produjo el pipeline y da un veredicto. Es solo lectura — sus herramientas no incluyen Write ni Edit. No puede tapar problemas editando. Solo puede juzgar. Esto es intencional.

Crea el archivo .claude/agents/reviewer.md:

---
name: reviewer
description: Final review of the full pipeline output. Fourth and last stage.
tools: Read, Grep, Bash
model: opus
---

You are a senior reviewer. You are read-only. You do not edit code.

1. Read the spec, the changes summary, and the test results from `.pipeline/`.
2. Run `git diff` to see the actual changes.
3. Assess: does the code match the spec? Are the tests meaningful or superficial? Any security, performance, or correctness issues?
4. Write a verdict to `.pipeline/review.md`:
   - VERDICT: SHIP / NEEDS WORK / BLOCK
   - For NEEDS WORK or BLOCK, list exactly what to fix and where.

Be the last line of defense. If the tests are green but the code is wrong, say BLOCK. Green tests are not the same as correct behavior.
SHIP Codigo correcto, pruebas significativas, nada que bloquee.
NEEDS WORK Problemas menores o mejoras recomendadas. No bloquea pero deberia atenderse.
BLOCK Error de correctitud, seguridad o comportamiento incorrecto. No se mergea.

Por que "pruebas verdes no es lo mismo que comportamiento correcto"

Un Tester puede escribir pruebas que pasan pero no prueban lo que importa. El Reviewer con Opus tiene la capacidad de leer las pruebas y detectar si son superficiales: si solo verifican que el codigo no explota, en lugar de verificar que el comportamiento es el correcto bajo las condiciones reales del dominio.

Por eso el Reviewer ejecuta sus propias comprobaciones con git diff y lee toda la cadena de produccion del pipeline, no solo el resultado final.

El Orquestador: Un Comando para los Cuatro

La pieza que convierte cuatro agentes separados en un pipeline. Un slash command que los invoca en orden, cada uno recogiendo el archivo de handoff del anterior.

Crea el archivo .claude/commands/ship.md:

Run the full feature pipeline for: $ARGUMENTS

Execute these stages in order. Do not skip ahead. After each stage, confirm the handoff file exists before starting the next.

1. Delegate to the `planner` subagent with the feature request above. Wait for `.pipeline/spec.md`.
2. If the spec has OPEN QUESTIONS, stop and show them to me. Otherwise delegate to the `coder` subagent. Wait for `.pipeline/changes.md`.
3. Delegate to the `tester` subagent. Wait for `.pipeline/test-results.md`. If tests failed, stop and show me the failures.
4. Delegate to the `reviewer` subagent. Show me `.pipeline/review.md`.

Report the final verdict. Do not merge anything. Leave the branch for my morning review.

Con este comando en su lugar, una sola linea activa toda la cadena:

$ /ship add rate limiting to the login endpoint

Claude Code ejecuta el Planner, espera spec.md, ejecuta el Coder, espera changes.md, ejecuta el Tester, verifica los resultados, y finalmente ejecuta el Reviewer. Si encuentra OPEN QUESTIONS o tests fallidos, se detiene y te muestra exactamente el problema. De lo contrario, cuando te despiertas tienes un review.md con el veredicto.

Estructura de Directorios Final

.claude/ agents/ planner.md ← El Planner (Opus) coder.md ← El Coder (Sonnet) tester.md ← El Tester (Sonnet) reviewer.md ← El Reviewer (Opus) commands/ ship.md ← El orquestador .pipeline/ ← Carpeta de handoffs (crear antes de correr) spec.md ← Planner escribe aqui changes.md ← Coder escribe aqui test-results.md ← Tester escribe aqui review.md ← Reviewer escribe aqui

La carpeta .pipeline/ existe en el repo pero sus archivos son efimeros: se sobreescriben en cada ejecucion del pipeline. Agregala a .gitignore o no — si la agregas al repo, tienes historial de los outputs del pipeline, lo cual puede ser util para auditorias.

Consideraciones de Modelo por Agente

La logica de Opus en las puntas, Sonnet en el medio

El pipeline usa Opus para Planner y Reviewer, Sonnet para Coder y Tester. Esto no es arbitrario:

  • Planner (Opus): El razonamiento sobre el codebase y la peticion es el punto donde la calidad mas importa. Un plan deficiente es costoso de recuperar.
  • Coder (Sonnet): Implementar una spec clara es trabajo mecanico de alta calidad. Sonnet lo hace bien y mas rapido que Opus.
  • Tester (Sonnet): Escribir pruebas contra una spec explicita es otro trabajo de implementacion. Sonnet es suficiente.
  • Reviewer (Opus): Detectar que algo esta mal cuando todo parece estar bien requiere razonamiento profundo. El Reviewer es el ultimo gate — merece Opus.

El costo total del pipeline es significativamente menor que usar Opus en los cuatro agentes, manteniendo la calidad donde mas importa.

Ejecucion Overnight: Donde Correrlo

Para la version overnight — donde el pipeline se ejecuta mientras duermes — necesitas infraestructura que mantenga una sesion de Claude Code activa. Las opciones principales:

  • Servidor cloud dedicado: Una instancia de EC2, Digital Ocean Droplet o similar con Claude Code instalado. El pipeline se ejecuta en servidores 24/7 sin tocar un servidor propio de produccion.
  • GitHub Actions: Configura un workflow que se dispara al crear un issue con cierta etiqueta. El pipeline corre en el runner de GitHub.
  • Cron local en un servidor siempre activo: Si tienes un servidor de desarrollo corriendo, un cron job puede disparar el pipeline en horarios programados.

La combinacion mas limpia para empezar: un servidor cloud economico (2 vCPU, 4GB RAM es suficiente) con Claude Code y el pipeline configurado. Cuesta menos de 20 USD al mes.

Este pipeline es directamente aplicable al Quarta Legal Hub. La adaptacion especifica para el proyecto:

Quarta Legal Hub Pipeline

Especifica endpoints nuevos del API o cambios al agente concursal. Conoce la estructura de Flask, los modelos de datos de procesos concursales y los patrones de respuesta del API existente. Lee las notas legales en Obsidian vault cuando la spec tiene implicaciones juridicas.

Patrones de Uso y Limites del Pipeline

Cuando NO usar el pipeline

  • Bugs urgentes en produccion: El pipeline es para features. Los bugs criticos necesitan intervencion directa.
  • Features con requisitos completamente ambiguos: Si no puedes describir la feature en una oracion, el Planner va a llenarla de OPEN QUESTIONS. Clarifica primero.
  • Cambios que requieren decision de arquitectura: Si la feature implica elegir entre dos enfoques arquitecturales, tu tienes que tomar esa decision antes de disparar el pipeline.

Cuando el pipeline brilla

  • Features bien definidas de tamano medio (2-8 horas de trabajo humano)
  • Endpoints de API nuevos con contratos claros
  • Migraciones de datos con logica verificable
  • Adicion de validaciones a flujos existentes
  • Integraciones con servicios externos bien documentados

Reiniciar una etapa especifica

Si el Tester encuentra fallos y necesitas solo reejecutar el Coder sin replantear la spec:

# En Claude Code, manualmente:
# 1. Lee .pipeline/test-results.md para entender el fallo
# 2. Decide si el fallo es del Coder o de la spec
# 3. Si es del Coder: edita .pipeline/spec.md con la correccion
#    y llama al coder subagent directamente
# 4. Si es de la spec: edita spec.md y reinicia desde el Coder
#    (no necesitas replantear todo desde el Planner)

Comprobacion de Conocimiento

1. Cual es el mecanismo que convierte cuatro agentes separados en un pipeline cohesionado?

Correcto. Los archivos de handoff en .pipeline/ son la clave. Cada agente escribe en un archivo predecible que el siguiente lee. Sin esta convencion, los agentes no se pueden encadenar automaticamente.
Incorrecto. El mecanismo es el archivo de handoff. Planner escribe spec.md, Coder lo lee y escribe changes.md, Tester lo lee y escribe test-results.md, Reviewer lee todo. Es simple y no requiere infraestructura especial.

2. Por que el Reviewer usa herramientas de solo lectura (Read, Grep, Bash) sin Write ni Edit?

Correcto. Las herramientas de solo lectura son una restriccion intencional. Si el Reviewer pudiera editar, podria ocultar problemas del Coder en lugar de reportarlos. El rol del Reviewer es juzgar, no arreglar.
Incorrecto. La restriccion a solo lectura es intencional y arquitectural. Fuerza al Reviewer a reportar los problemas en lugar de parchearlos silenciosamente. Si pudiera editar, contaminaria la separacion de roles del pipeline.

3. El Planner usa Opus y el Coder usa Sonnet. Cual es la razon principal de esta diferencia?

Correcto. La logica es que Opus donde el razonamiento profundo importa (Planner, Reviewer) y Sonnet donde la tarea es de implementacion contra instrucciones claras (Coder, Tester). Optima calidad y costo.
Incorrecto. La diferencia es cualitativa: el Planner necesita razonar profundamente sobre el codebase y la peticion para producir una spec sin ambiguedades. Eso requiere Opus. Implementar esa spec es mecanicamente demandante pero no requiere el mismo nivel de razonamiento — Sonnet lo hace bien.

4. Que debe hacer el Tester si encuentra que un test falla?

Correcto. El Tester escribe los fallos en test-results.md y para. No arregla el codigo porque eso contaminaria la separacion de roles. El pipeline pausa y el humano decide el siguiente paso.
Incorrecto. El Tester debe escribir los fallos en test-results.md y detenerse ahi. Si arregla el codigo el mismo, el Coder nunca sabe que su implementacion tenia un bug y el arreglo puede ser inconsistente con los patrones del codebase.

5. Que condicion hace que el orquestador (slash command /ship) pause y muestre informacion antes de continuar?

Correcto. El orquestador tiene dos puntos de pausa humana: (1) si spec.md tiene OPEN QUESTIONS, muestra las preguntas y espera respuesta; (2) si test-results.md tiene fallos, muestra los fallos y detiene el pipeline.
Incorrecto. El orquestador tiene dos puntos de pausa explicitos: cuando la spec tiene OPEN QUESTIONS (el Planner no pudo resolver ambiguedades) y cuando los tests fallan. Ambas situaciones requieren decision humana antes de continuar.
