Workflows Multi-Agente: Guia Completa (11 Modulos)

Introduccion

La experiencia practica es contundente: usar agentes unicos durante doce meses y luego cambiar a workflows multi-agente en dos dias revela una diferencia arquitectonica fundamental que ningun tutorial captura completamente.

Los sistemas multi-agente en 2026 tienen una sola pregunta definitoria: como coordinas agentes que no pueden compartir contexto sin envenenarse mutuamente? La respuesta determina si tu sistema escala o colapsa bajo carga real.

Este curso construye tu modelo mental desde los primitivos fundamentales, luego conecta cada concepto directamente a lo que los Dynamic Workflows de Claude Code te dan hoy. Once modulos. Cada uno cierra una brecha conceptual que hace que los sistemas multi-agente fallen en produccion.

MODULO 1 Que es un Sistema Multi-Agente

La distincion mas importante que existe en esta disciplina:

El agente es la UNIDAD: una instancia LLM con su propio system prompt, conjunto de herramientas, ventana de memoria y a veces su propio modelo subyacente.

El sistema multi-agente es el RUNTIME: la maquineria que coordina dos o mas agentes, enruta tareas entre ellos, maneja handoffs y aplica una capa de gobierno sobre todo el conjunto.

Esta distincion importa porque la mayoria de fallas en sistemas multi-agente son fallas del RUNTIME, no fallas del agente. Los agentes individuales frecuentemente razonan correctamente. El sistema falla en coordinacion, propagacion de contexto y limites de permisos. Atacar el problema en el lugar equivocado — mejorando los agentes cuando el runtime esta roto — es la causa principal de iteraciones interminables sin progreso.

Por Que los Agentes Unicos Fallan a Escala

Tres problemas estructurales hacen que los agentes unicos colapsen en trabajos grandes:

  • Context saturation: cada resultado intermedio consume la ventana de contexto. A escala, el agente esta razonando sobre un monton de su propia historia en lugar del problema actual. La calidad del razonamiento cae con cada paso adicional.
  • Sequential bottleneck: el agente ejecuta un paso a la vez. Una migracion de 200 archivos que podria paralelizarse corre en serie durante horas. No hay forma de acortar este tiempo dentro del modelo de agente unico.
  • Fragile recovery: si el agente falla o deriva a mitad de tarea, todo el trabajo se reinicia desde cero. No hay checkpoints. No hay recuperacion parcial.

Los sistemas multi-agente resuelven los tres problemas distribuyendo trabajo entre agentes aislados, almacenando resultados intermedios fuera del contexto de cualquier agente y agregando puntos de recuperacion a nivel de fase.

MODULO 2 Los Tres Primitivos de Orquestacion de Claude

Claude Code ofrece tres primitivos de orquestacion con caracteristicas fundamentalmente diferentes. Elegir el incorrecto produce sistemas que funcionan en demos pero fallan en produccion.

Primitivo Que es Donde vive el estado Repetible Escala max
Subagents Instancias Claude aisladas generadas por la sesion principal, reportan solo al orquestador Contexto de la sesion principal No Pocos por turno
Agent Teams Multiples sesiones Claude Code coordinadas por un team lead, pueden enviarse mensajes directamente via mailbox Contexto propio de cada sesion No Sesiones paralelas
Dynamic Workflows Script de orquestacion JavaScript que Claude escribe; un runtime separado lo ejecuta en hasta 1000 agentes Variables del script, fuera de todos los contextos Si (guardar como slash command) 1000 agentes / 16 concurrentes

Regla de Decision

  • Usa subagentes cuando necesites una o dos investigaciones aisladas que reporten de vuelta a una sesion unica. Trabajo ad-hoc sin necesidad de repeticion.
  • Usa agent teams cuando los companieros necesitan comunicarse directamente entre si y contigo, sin pasar por un orquestador central. Coordinacion lateral importa.
  • Usa dynamic workflows cuando la orquestacion debe ser repetible, el plan debe sobrevivir limites de contexto, o el trabajo toma horas o dias y necesita recuperacion por checkpoints.

MODULO 3 Las Seis Topologias de Orquestacion

Las topologias son los patrones estructurales de como los agentes se conectan entre si. Cada una resuelve un problema distinto y tiene un failure mode distinto. Usarlas correctamente empieza por entender cuando cada una es la opcion apropiada.

1Sequential Pipeline

Agentes dispuestos en cadena. El Agente A produce output, lo pasa al Agente B, que lo pasa al Agente C.

[A: Parse] → [B: Analyze] → [C: Format] → [Output Final]

Cuando usar: trabajo estrictamente dependiente donde cada paso debe completarse antes de que empiece el siguiente. Facil de depurar porque los datos tienen un solo camino.

Implementacion Claude: cadena de prompts dentro de un script de dynamic workflow. Cada fase ejecuta un subagente, espera completitud, pasa el resultado como input al siguiente.

FAILURE MODE

La latencia se compone. Si el Agente B es lento, todo el pipeline espera. No usar para trabajo con caminos paralelos independientes donde el tiempo importa.

2Coordinator-Worker (Hub and Spoke)

Un agente coordinador recibe la tarea de alto nivel, la descompone en subtareas y enruta cada una a un worker especialista. Los workers devuelven resultados al coordinador, que sintetiza el output final.

Cuando usar: trabajo que se descompone en dominios especializados distintos. La logica de enrutamiento es estable y conocible en tiempo de plan.

FAILURE MODE

Punto unico de falla en el coordinador. Si el contexto del coordinador se llena o deriva, todo el sistema se degrada. Mantener el contexto del coordinador estrecho es critico.

3Parallel Fan-Out with Merge

Multiples agentes trabajan simultaneamente en subtareas independientes. Un paso de merge recolecta y reconcilia sus outputs en un resultado unificado.

Cuando usar: subtareas sin dependencias entre ellas. Auditar 200 archivos, consultar multiples fuentes de datos, ejecutar cinco investigaciones de bugs simultaneamente.

Performance gain: la ejecucion paralela corta el tiempo de procesamiento 60-80% para tareas sin dependencias de pasos.

FAILURE MODE

La logica de merge es la parte dificil. Si los agentes devuelven schemas inconsistentes o hallazgos conflictivos, un merge naive produce basura. Los contratos de output son obligatorios.

4Generator-Verifier

Un agente genera output. Un segundo agente lo evalua contra criterios explicitos. El resultado retroalimenta al generador. El loop corre hasta que el output pasa los criterios o se alcanza un conteo maximo de iteraciones.

Cuando usar: la calidad del output es critica y los criterios de evaluacion pueden escribirse explicitamente. Escritura de pruebas, hallazgos de seguridad, planes de migracion.

FAILURE MODE

Si los criterios del verificador son vagos, se convierte en un sello de goma que aprueba todo. Escribe los criterios de verificacion como reglas explicitas y verificables, no como principios generales.

5Shared-State

Los agentes coordinan a traves de un store persistente que todos leen y escriben directamente. Ningun orquestador central enruta mensajes; el store compartido es el mecanismo de coordinacion.

Cuando usar: agentes construyen progresivamente sobre los hallazgos de los demas. El contexto que descubre un agente es inmediatamente util para otros trabajando el mismo problema.

Implementacion Claude: en la practica, esto es el filesystem en un git worktree o una carpeta docs estructurada. Cada decision, cada plan, cada item completado cae en la carpeta como un archivo Markdown. Cada agente lo lee al inicio de su turno.

FAILURE MODE

Envenenamiento de contexto. Un agente escribe un mal hallazgo al store compartido. Cada agente downstream lo lee como verdad absoluta y construye sobre el. El error se compone a traves del pipeline sin que nadie lo detecte.

6Debate (Adversarial Multi-Agent)

Dos o mas agentes atacan el mismo problema desde posiciones opuestas. Un agente juez —o el orquestador— reconcilia el output del debate en un hallazgo sintetizado.

Cuando usar: quieres hallazgos que sobrevivan presion adversarial antes de llegarte. Auditorias de seguridad, evaluaciones de riesgo de migracion, decisiones de arquitectura criticas.

Implementacion Claude: "Los agentes abordan el problema desde angulos independientes. Otros agentes luego intentan refutar lo que encontraron. El run itera hasta que las respuestas convergen o la divergencia en si misma es el hallazgo."

MODULO 4 Arquitectura de Comunicacion

La decision de diseno critica no es que formato de mensaje usar. Es si los agentes se comunican directamente o a traves de un sustrato.

Comunicacion Directa Agente-a-Agente

El Agente A envia su output directamente al contexto del Agente B. RIESGO: el Agente B hereda los errores, sesgos y alucinaciones del Agente A. Si el Agente A alucinó un dato, el Agente B lo toma como verdad.

Comunicacion Mediada por Sustrato

Los agentes escriben a un store compartido (variables del script, filesystem, base de datos). Otros agentes leen desde ahi. BENEFICIO: el contexto es controlado; las malas escrituras son aislables y auditables.

Regla practica de sistemas de produccion: "Los agentes no deben hablarse directamente. Deben escribir a una capa de memoria compartida y leer desde ella. El conocimiento canonico vive en un lugar. Cada agente opera en aislamiento con un rol definido, herramientas definidas y outputs definidos."

Output Contracts

Cada agente en un sistema de produccion necesita un contrato de output explicito: un schema que define exactamente lo que debe devolver. Sin el, el paso de merge y los agentes downstream tienen que adivinar lo que recibieron, produciendo comportamiento impredecible.

Context Window Budgeting

  • Mantener el orquestador estrecho: su trabajo es descomposicion y enrutamiento. El razonamiento de dominio pertenece a los agentes especialistas, no al orquestador.
  • Limitar lo que reciben los agentes: pasa solo lo que el agente necesita para su tarea especifica. No el historial completo del workflow.
  • Limite de hot path para memoria a corto plazo: en loops agenticos, mantener solo los ultimos 3-5 intercambios en contexto activo. El resto va al store compartido.

MODULO 5 Modos de Falla

Los cinco fallos que matan sistemas multi-agente de produccion. Cada uno es predecible y prevenible con las salvaguardas correctas.

FALLO 1 — Context Poisoning

Un agente escribe un output malo (hallazgo alucinado, schema incorrecto, estado corrupto) al store compartido. Los agentes downstream lo leen como verdad y construyen sobre el. El error se compone a traves del pipeline.

Signos en produccion: hallazgos que parecen plausibles pero no pueden rastrearse de vuelta al contenido real del archivo.

PREVENCION

Validacion de schema en cada punto de escritura al store compartido. Agentes verificadores revisan outputs antes de que lleguen al store. Nunca pasar un output directo al siguiente agente sin validacion intermedia.

FALLO 2 — Cascading Failure

Un agente falla. El orquestador no aisla el fallo y enruta el mal resultado downstream. Los agentes construidos sobre el output fallido tambien fallan. Tasa de fallo documentada: 41-86.7% en sistemas sin orquestacion apropiada.

PREVENCION

Circuit breakers: si un agente devuelve error o null output, detener esa rama inmediatamente. Scoring de confianza en checkpoints del pipeline. Cada fase debe tener un criterio explicito de "lo que cuenta como exito".

FALLO 3 — Scope Creep

La descomposicion del orquestador es demasiado amplia. Los agentes interpretan su mandato de forma expansiva. Un agente encargado de "auditar el codebase" empieza a editar archivos que no debia tocar.

PREVENCION

Cada agente obtiene un scope explicito y acotado en su task prompt: que archivos puede leer, que puede escribir, que operaciones estan prohibidas. Politica de edicion: solo lectura a menos que se otorgue explicitamente acceso de escritura en el task prompt.

FALLO 4 — Silent Substitution

Un agente no puede completar un paso y silenciosamente inserta datos placeholder detras de un try/catch. Reporta exito. El pipeline trata el placeholder como un resultado real. El error no se descubre hasta que el output final es inutilizable.

PREVENCION

En CLAUDE.md: "NUNCA sustituyas datos mock o placeholder por un resultado real. Si un paso falla, reporta el error explicitamente y detente. Un fallo reportado es recuperable. Un fallo silencioso no lo es."

FALLO 5 — Coordination Deadlock

Dos agentes se esperan mutuamente. El Agente A no puede continuar hasta que el Agente B termine. El Agente B no puede empezar hasta que el Agente A escriba al store compartido. El workflow se paraliza indefinidamente.

PREVENCION

Grafos de dependencia explicitos en el script del workflow: cada agente declara lo que necesita antes de empezar. Timeouts en cada invocacion de agente. Si el timeout se alcanza, esa rama se marca como fallida y el workflow continua o se detiene segun la politica configurada.

MODULO 6 La Capa de Gobierno

Cada sistema multi-agente necesita tres capas estructurales para funcionar de forma confiable:

Capa Rol Que se rompe sin ella
Orchestrator Descompone tareas, enruta a especialistas, sintetiza resultados finales Sin coordinacion; agentes duplican o conflictuan trabajo
Specialist Agents Ejecutan operaciones acotadas con prompts y herramientas enfocados en dominio Cuello de botella de contexto unico; sin paralelismo posible
Governance Layer Controla lo que cada agente puede acceder, cuando puede actuar, que debe registrar Acceso sin restricciones a herramientas; trails de auditoria faltantes; outputs no validados llegando a sistemas downstream

Las Cuatro Funciones de la Capa de Gobierno

  1. Permission scoping: cada agente tiene un conjunto de permisos declarado. Un agente de auditoria de seguridad obtiene acceso de solo lectura. Un agente de migracion obtiene acceso de escritura solo a los paths especificados en el task prompt.
  2. Human-in-the-loop gates: define que acciones requieren aprobacion humana antes de ejecutarse. Las operaciones irreversibles —borrado de archivos, escritura en base de datos de produccion, deploy a infraestructura— siempre pasan por una HITL gate.
  3. Audit trails: cada decision, accion y llamada a herramienta del agente se registra con el ID del agente y el razonamiento que la llevo. Sin esto, depurar un fallo de produccion es imposible.
  4. Blast radius limits: define el dano maximo que un agente puede causar si se porta mal. Un agente que solo puede escribir a una carpeta especifica tiene un blast radius acotado aunque aluciné o sea comprometido.

Ejemplo de CLAUDE.md para governance:

## Agent Permissions
- Read access: entire repository
- Write access: only paths listed in the task prompt
- Shell commands: only commands on the approved list
- Network: no external calls unless the task prompt specifies an endpoint

## Error Handling
- Silent failures are not permitted
- Every error must be reported before halting

## Irreversible Action Policy
- Database writes require explicit approval in the task prompt
- File deletions require explicit approval in the task prompt

MODULO 7 Los Cinco Patrones Claude-Nativos en Produccion

1Prompt Chaining

Rompe una tarea compleja en una cadena de prompts simples. El output de uno se convierte en el input del siguiente. Cada prompt en la cadena tiene una responsabilidad unica y acotada.

Cuando usar: la tarea tiene etapas secuenciales claras donde cada etapa depende del output de la anterior. La cadena hace explicita la dependencia y facilita la depuracion.

2Routing

Un agente clasificador lee el input y lo enruta al especialista apropiado. El clasificador no procesa la tarea; solo lee, clasifica y delega. El especialista tiene el contexto correcto para la tarea especifica.

Cuando usar: las tareas llegan en un stream heterogeneo donde cada tipo requiere un tratamiento fundamentalmente diferente. El enrutador reduce el contexto que cada especialista necesita cargar.

3Parallelization

Distribuye subtareas independientes a multiples agentes simultaneamente. Merge de resultados al final. Los workflows de Claude corren hasta 16 agentes concurrentes.

Performance: el uso de tokens cae 60-90% vs encadenamiento secuencial para tareas sin dependencias. La reduccion de tiempo de ejecucion es proporcional al numero de agentes paralelos hasta el limite de concurrencia.

4Orchestrator-Subagents

Un orquestador recibe un objetivo de alto nivel, lo descompone en subtareas, despacha a subagentes especializados y sintetiza sus outputs. El unico trabajo del orquestador es descomposicion y sintesis. El razonamiento de dominio pertenece a los especialistas.

Esta division de responsabilidades es lo que mantiene el contexto del orquestador estrecho y funcional durante workflows largos.

5Evaluator-Optimizer

El agente generador produce output. El agente evaluador lo puntua contra criterios explicitos. La puntuacion mas feedback regresa al generador. Loop hasta que el output pasa o se alcanzan las iteraciones maximas.

Critico: establece un conteo maximo de iteraciones de 3 a 5. Sin el, el loop puede correr indefinidamente consumiendo tokens sin convergencia real.

MODULO 8 Diseno de Sistema desde Cero

Proceso repetible para disenar un sistema multi-agente antes de escribir un solo prompt del workflow. Saltarse este proceso produce sistemas que hay que redisenar desde cero despues de la primera ejecucion real.

STEP 1Task Decomposition

Escribe la tarea de alto nivel en una oracion. Luego lista cada operacion distinta necesaria para completarla. Para cada operacion, responde dos preguntas: depende del output de otra operacion? puede correr al mismo tiempo que otras? Las respuestas definen el grafo de dependencias del workflow.

STEP 2Specialist Identification

Para cada operacion en tu diagrama de fases, identifica el agente especialista que necesita. Define para cada agente: el rol en una oracion, acceso a herramientas exacto, contrato de output (schema JSON explicito) y comportamiento en falla.

STEP 3Communication Design

Decide: sustrato-mediado o directo? Para la mayoria de sistemas de produccion la respuesta es sustrato-mediado via variables del script del workflow o el filesystem. La comunicacion directa es la excepcion, no la regla.

STEP 4Governance Contracts

Escribe las reglas CLAUDE.md del agente antes de escribir cualquier prompt del workflow. Los contratos de governance definen los limites dentro de los cuales todos los prompts operan.

STEP 5Pre-Flight Checklist

Antes de correr cualquier workflow multi-agente en un repositorio real:

  • Trabajando en un git worktree o feature branch, no en main
  • El scope de permisos de cada agente esta explicitamente acotado en el task prompt
  • Contratos de output definidos para cada agente que escribe al store compartido
  • Agentes verificadores en su lugar para cada agente generador en caminos criticos
  • HITL gates definidas para todas las acciones irreversibles
  • Conteos maximos de iteraciones establecidos en todos los loops evaluador-optimizador

MODULO 9 Construyendo con el Stack de Orquestacion de Claude

La arquitectura practica combina dos primitivos en capas:

Capa Exterior: Dynamic Workflow

Claude escribe el script de orquestacion. El script maneja descomposicion del objetivo, fan-out de tareas paralelas, recoleccion de resultados y secuenciacion de fases. El estado intermedio vive en variables del script, fuera del contexto de cualquier agente individual.

El script puede guardarse como slash command y reutilizarse: la orquestacion se convierte en un artefacto, no en trabajo que se rehace cada vez.

Capa Interior: Specialist Subagents

Cada fase en el workflow despacha subagentes especialistas. Cada subagente tiene: un system prompt con scope via la task en el workflow, rutas de archivo especificas, schema de output definido y una politica de falla explicita.

Los especialistas no saben que son parte de un workflow. Solo ven su task y sus herramientas. Esto es lo que mantiene su razonamiento limpio y enfocado.

Observabilidad: /workflows Command

El comando /workflows da observabilidad en vivo a cada dynamic workflow en ejecucion: estado a nivel de fase, drill-down a nivel de agente, capacidad de pausar o reiniciar agentes individuales o detener todo el workflow. En produccion, esta visibilidad es lo que hace que los sistemas multi-agente sean manejables en lugar de cajas negras.

MODULO 10 Escala y Control de Costos

Los sistemas multi-agente no tienen curvas de costo lineales. Los costos se componen con el conteo de agentes. Entender la arquitectura de costos evita sorpresas en produccion.

Arquitectura de Costos por Capa

  1. Orchestration planning: escribir el script o descomponer la tarea cuesta tokens por adelantado. Este costo es fijo por trabajo, no por agente. Se amortiza sobre toda la ejecucion del workflow.
  2. Agent execution: cada agente lee su tarea, lee sus archivos de input, llama herramientas y produce output. El costo escala linealmente con el conteo de agentes. Este es el driver principal del costo total.
  3. Synthesis: el orquestador lee todos los outputs del agente y sintetiza. El costo escala con el volumen total de output de todos los agentes. Un merge de 100 agentes con outputs grandes puede costar mas que la ejecucion de todos los agentes.

La Regla de 3-7 Agentes

Mantener equipos pequenos: 3-7 agentes por fase del workflow. Mas alla de ese rango, crear estructuras jerarquicas: un team lead por grupo, los team leads reportan a un orquestador global.

Las arquitecturas planas con 20+ agentes en una sola capa de coordinacion tienen overhead cuadratico de comunicacion. La jerarquia no es burocracia; es ingenieria de escala.

MODULO 11 Guia de Decision

La pregunta que mas tiempo pierde la gente: "debo usar multi-agente o agente unico?" La respuesta depende de caracteristicas especificas del trabajo, no de preferencias.

CONSTRUIR MULTI-AGENTE CUANDO:

  • La tarea tiene caminos paralelos genuinamente independientes (y puedes enumerarlos)
  • El trabajo excede la ventana de contexto de un solo agente y no puede resumirse sin perdida
  • Necesitas verificacion adversarial del output
  • El trabajo corre por horas o dias y necesita recuperacion por checkpoints
  • El proceso es repetible y la orquestacion misma deberia ser un artefacto reutilizable

QUEDARSE CON AGENTE UNICO CUANDO:

  • La tarea es secuencial sin paralelismo real
  • El trabajo cabe comodamente en una ventana de contexto
  • El overhead de coordinacion excederia el tiempo de ejecucion
  • Todavia estas construyendo y cambiando el sistema rapidamente

El Error Arquitectonico Mas Grande

Enrutar todos los resultados de los agentes de vuelta al contexto del orquestador. Una vez que haces eso, has reconstruido el cuello de botella del agente unico con extra network hops. El contexto del orquestador deberia contener el plan y la sintesis final. Nada mas. Todo lo que llega al orquestador mas alla de eso es ruido que degrada su capacidad de razonamiento.
