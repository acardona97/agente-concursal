Prompt Caching — reducir costos hasta 90%

Cómo evitar que el agente re-procese la Ley 1116 en cada consulta
Concepto

Prompt caching es una feature de la API de Anthropic que guarda en memoria partes de tu prompt por hasta 5 minutos. Si la siguiente consulta tiene el mismo prefijo cacheado, Anthropic cobra solo el 10% del costo normal por esos tokens — y los procesa más rápido.

El caso perfecto para caching: tu agente carga la Ley 1116 (miles de tokens) como contexto en cada consulta. Sin caché, pagas esos tokens completos 50 veces al día. Con caché, los pagas completos una vez y el 10% las otras 49 veces.

La condición: el prefijo cacheado debe ser idéntico entre consultas (mismo system prompt, mismo texto de la ley) y el gap entre consultas no puede superar 5 minutos (caché ephemeral) o 1 hora (si la API lo extiende).

Cómo funciona — activación y estructura
CONSULTA 1 (cache MISS — paga precio completo): ─────────────────────────────────────────────── [System: "Eres agente concursal..."] ← cacheable [Contexto: Ley 1116 completa, 8000 tok] ← cacheable ← MARCAR AQUÍ [User: "¿Término para objetar créditos?"] → Anthropic procesa TODO, guarda el prefijo en caché → Cobra: 8000 + 50 (system) tokens de input CONSULTA 2, 3, 4... (cache HIT — paga 10%): ──────────────────────────────────────────── [System: "Eres agente concursal..."] ← idéntico [Contexto: Ley 1116 completa, 8000 tok] ← idéntico ← HIT [User: "¿Qué es la primera clase?"] ← nuevo → Anthropic reutiliza caché para los 8050 tokens del prefijo → Cobra: 8050 * 0.10 + tokens nueva pregunta → AHORRO: 90% de 8050 tokens por consulta CONDICIONES: ──────────── ✓ El texto cacheado debe ser bit-a-bit idéntico ✓ Mínimo 1024 tokens para cachear (no vale para prompts cortos) ✓ cache_control: {"type": "ephemeral"} en el bloque a cachear ✓ Caché dura 5 minutos (ephemeral) — se renueva en cada uso
Cálculo real — agente concursal con Ley 1116

El agente concursal carga ~7 fragmentos de la Ley 1116 por consulta (N_RESULTADOS = 7, cada fragmento ~900 caracteres ≈ 225 tokens). Total contexto: ~1,575 tokens. Si cargas la Ley 1116 completa como contexto estático (sin RAG), son ~8,000 tokens. Asumamos RAG con 1,575 tokens de contexto normativo estático.

Código — agregar caché al agente concursal
import anthropic
import os

client = anthropic.Anthropic(api_key=os.environ.get("ANTHROPIC_API_KEY"))

# Texto de la Ley 1116 (o los fragmentos RAG del sistema)
# Este texto debe ser IDÉNTICO en todas las consultas para que el caché funcione
CONTEXTO_NORMATIVO_BASE = """
[Aquí va el texto de la Ley 1116 o los artículos que siempre cargas.
Mínimo 1024 tokens para que el caché se active.]
...
"""

def consultar_con_cache(pregunta: str, contexto_proceso: str = ""):
    """
    Estructura optimizada para prompt caching.
    El contexto normativo base se cachea, el contexto del proceso no.
    """
    messages = client.messages.create(
        model="claude-opus-4-5",
        max_tokens=4096,
        system=[
            # Bloque 1: System prompt — también cacheable si es largo
            {
                "type": "text",
                "text": "Eres agente concursal colombiano experto en Ley 1116...",
                "cache_control": {"type": "ephemeral"}  # ← CACHEAR esto
            }
        ],
        messages=[
            # Bloque 2: Contexto normativo estático — el más importante para cachear
            {
                "role": "user",
                "content": [
                    {
                        "type": "text",
                        "text": f"<contexto_normativo>\n{CONTEXTO_NORMATIVO_BASE}\n</contexto_normativo>",
                        "cache_control": {"type": "ephemeral"}  # ← CACHEAR esto
                    },
                    # Contexto del proceso específico — NO se cachea (cambia por consulta)
                    {
                        "type": "text",
                        "text": f"<contexto_proceso>\n{contexto_proceso}\n</contexto_proceso>\n\n<pregunta>\n{pregunta}\n</pregunta>"
                        # Sin cache_control → siempre se procesa fresco
                    }
                ]
            }
        ]
    )

    # Ver métricas de caché en la respuesta
    uso = messages.usage
    print(f"Tokens entrada: {uso.input_tokens}")
    print(f"Cache escritura: {uso.cache_creation_input_tokens}")  # primera vez
    print(f"Cache lectura: {uso.cache_read_input_tokens}")       # hits subsiguientes

    return messages.content[0].text
Quiz — 3 preguntas
Pregunta 1 / 3
El agente concursal usa RAG: en cada consulta, ChromaDB recupera 7 fragmentos diferentes de la Ley 1116 según la pregunta. ¿Estos 7 fragmentos se pueden cachear de forma eficiente? ¿Por qué?
No, eficientemente no. El caché requiere que el texto sea bit-a-bit idéntico. Si cada consulta recupera fragmentos diferentes (diferentes artículos de la Ley 1116), el prefijo cambia y el caché nunca hace hit. Lo que sí se puede cachear eficientemente es el contexto normativo estático: el system prompt, los artículos que siempre se incluyen (Art. 49-52, Art. 2495 C.C.), y el historial de conversación acumulado. Los fragmentos RAG dinámicos van al final, sin cache_control.
Pregunta 2 / 3
¿Qué sucede si entre dos consultas pasan más de 5 minutos y el caché expira? ¿El sistema falla o simplemente deja de ahorrar?
El sistema no falla — simplemente pierde el ahorro temporalmente. Cuando el caché expira, Anthropic procesa el prefijo completo otra vez (cache MISS), cobra el precio normal, y crea un nuevo caché para las siguientes 5 minutos. El comportamiento funcional del agente es idéntico con o sin caché. El caché es transparente para el usuario final — solo afecta la factura.
Pregunta 3 / 3
Para maximizar el ahorro con caché en el agente concursal, ¿cuál es el orden correcto de los bloques en el prompt (de más a menos estático)?
Orden óptimo (más estático primero): 1. System prompt (rol, capacidades, restricciones) — nunca cambia 2. Contexto normativo base (artículos de Ley 1116 siempre incluidos) 3. Historial de conversación (crece pero es estable dentro de una sesión) 4. Fragmentos RAG (semi-dinámicos, cambian por consulta) 5. Pregunta actual del usuario (siempre nueva)

Poner cache_control en los bloques 1-3. Los bloques 4-5 van sin caché. El caché de la API siempre se aplica al prefijo — todo lo que está antes del último bloque sin cache_control.
