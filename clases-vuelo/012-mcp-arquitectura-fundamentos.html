El protocolo MCP: qué pasa exactamente

MCP (Model Context Protocol) es un protocolo abierto de Anthropic que estandariza cómo los modelos de lenguaje se comunican con sistemas externos. La analogía legal: MCP es como el reglamento de una audiencia. Define quién habla primero, qué formato tienen los escritos, cómo se notifican las decisiones.

Analogía concursal

Sin MCP, cada app habla con Claude de forma diferente — como si cada juzgado tuviera su propio formato de escritos. Con MCP, hay un estándar: el cliente siempre sabe cómo presentar una solicitud y el servidor siempre sabe cómo responder.

El handshake: cómo se establece la conexión

Cuando Claude se conecta a tu servidor MCP, hay una negociación inicial en tres pasos:

┌─────────────────────────────────────────────────────────────────┐ │ HANDSHAKE MCP │ └─────────────────────────────────────────────────────────────────┘ 1. INITIALIZE Claude ──→ Servidor { "method": "initialize", "params": { "protocolVersion": "2024-11-05", "clientInfo": { "name": "Claude", "version": "..." }, "capabilities": { "roots": {}, "sampling": {} } } } Servidor ──→ Claude { "result": { "protocolVersion": "2024-11-05", "serverInfo": { "name": "Agente Concursal Quarta" }, "capabilities": { "tools": {}, "resources": {} } } } 2. DISCOVERY (tools/list) Claude ──→ Servidor { "method": "tools/list" } Servidor ──→ Claude { "result": { "tools": [ ...definiciones... ] } } 3. TOOL CALL (cuando Claude decide usarla) Claude ──→ Servidor { "method": "tools/call", "params": { "name": "consultar_agente_concursal", "arguments": { "consulta": "..." } } } Servidor ──→ Claude { "result": { "content": [{ "type": "text", "text": "..." }] } }
Clave: Todo viaja como JSON-RPC 2.0. Cada mensaje tiene jsonrpc: "2.0", un id para correlacionar respuestas, y un method. Nada de APIs REST ad-hoc — es un protocolo bidireccional estricto.

Los 3 tipos de capacidades MCP

MCP define exactamente tres primitivas. No inventes más — si algo no encaja en estas tres, repensá el diseño.

RESOURCES

Datos pasivos

Contenido que Claude lee sin ejecutar código. Como expedientes en el archivo del juzgado. Claude puede consultarlos, no modificarlos.

Ejemplos:
• El texto de la Ley 1116
• Un expediente PDF
• Una lista de acreedores

TOOLS

Acciones ejecutables

Funciones que Claude llama con parámetros y recibe un resultado. Como pedirle al actuario que busque un radicado específico.

Ejemplos:
• buscar_en_csj(termino)
• calcular_prelacion(creditos)
• generar_escrito(tipo, datos)

PROMPTS

Plantillas reusables

Templates de prompts que el servidor expone. El usuario puede invocarlos desde la UI. Como un modelo de escrito que llenas con los datos del caso.

Ejemplos:
• /calificar-creditos
• /redactar-objecion
• /analizar-acuerdo

¿Cuándo usar cada uno?

Resources: cuando el contenido es estático o casi estático (normas, templates, configuración).
Tools: cuando necesitas ejecutar lógica, consultar APIs externas, o hacer cálculos.
Prompts: cuando quieres darle al usuario atajos predefinidos para tareas frecuentes.

Transport layers: stdio vs HTTP/SSE

MCP puede viajar por dos "canales" diferentes. La elección importa según dónde corre tu servidor.

Característica stdio HTTP + SSE
¿Cómo funciona? Proceso local, stdin/stdout HTTP requests + Server-Sent Events
¿Dónde vive el servidor? Mismo computador que el cliente Cualquier lugar (Railway, cloud)
¿Para qué sirve? Claude Code CLI, herramientas locales Claude.ai web, agentes remotos
¿Necesita autenticación? No (mismo proceso) Sí (HTTPS + tokens)
Latencia Milisegundos Depende de la red
Tu agente concursal — Este es el tuyo (Flask en Railway)
Analogía de transporte

stdio es como hablar con tu secretaria que está en la misma oficina — comunicación instantánea, sin formalidades.
HTTP/SSE es como comunicarte con la Supersociedades por correo certificado: hay protocolo, hay autenticación, pero funciona desde cualquier parte del país.

SSE: por qué existe el Server-Sent Events

HTTP normal es request-response: tú preguntas, el servidor responde, se cierra la conexión. Pero MCP necesita que el servidor pueda enviar mensajes en cualquier momento (notificaciones, actualizaciones de progreso). SSE mantiene la conexión abierta para que el servidor pueda hablar cuando quiera.

# Así se ve una conexión SSE en Flask
# El cliente abre GET /sse y la conexión queda abierta
# El servidor puede enviar eventos cuando quiera

@app.route("/sse")
def sse_stream():
    def generate():
        # Primer mensaje: anunciar el endpoint de mensajes
        yield f"event: endpoint\ndata: /messages\n\n"
        # Luego el cliente envía POSTs a /messages
        # y este stream devuelve las respuestas
    return Response(generate(), mimetype="text/event-stream")

Cómo Claude descubre y llama tools MCP

Esto es lo que pasa cuando conectas tu servidor MCP a Claude.ai y haces una pregunta:

Claude SÍ → "consultar_agente_concursal" encaja con esto FASE 3: Claude decide llamar la tool Claude genera internamente: { use_mcp_tool: { server: "agente-concursal-quarta", tool: "consultar_agente_concursal", arguments: { "consulta": "proyecto de calificación proceso X" } } } FASE 4: Ejecución Claude ──→ Servidor: tools/call { name: ..., arguments: ... } Servidor ──→ tu agente.py → ChromaDB → Claude API → respuesta Servidor ──→ Claude: { content: [{ type: "text", text: "..." }] } FASE 5: Claude responde al usuario Claude integra el resultado de la tool en su respuesta final Puede encadenar otra tool si necesita más información Claude responde al usuario con el resultado procesado FASE 6: Iteración (tool chaining) Claude puede llamar MÚLTIPLES tools antes de responder Claude puede llamar una tool, evaluar el resultado, y llamar otra Ejemplo: buscar_jurisprudencia() → obtener_sentencia() → redactar_escrito()

Por qué MCP es mejor que llamar funciones directamente

Tienes razón en preguntar esto: ¿por qué no simplemente llamar consultar_agente(mensaje) directamente? La respuesta tiene cuatro partes:

1. Descubrimiento automático
Con MCP, Claude aprende qué puede hacer consultando tools/list. No necesitas hardcodear en el sistema prompt "puedes usar la función X". Claude lo descubre solo y decide cuándo es apropiado usarla.
2. Interoperabilidad
Tu servidor MCP puede ser usado por Claude.ai web, Claude Code CLI, cualquier cliente MCP futuro, y otros agentes. Sin MCP, cada integración requiere código específico. Con MCP, uno funciona para todos.
3. Composabilidad
Claude puede combinar tools de diferentes servidores en una sola tarea. Puede llamar tu tool de derecho concursal y simultáneamente llamar otra tool de un servidor de calendarios para agendar la audiencia. Sin MCP, eso requiere orquestación manual.
4. Separación de responsabilidades
Tu servidor MCP no sabe nada de Claude. Claude no sabe nada de tu base de datos. Cada uno hace su trabajo. Si mañana cambias de ChromaDB a PostgreSQL, Claude ni se entera — solo le importa el contrato MCP.
Quarta Legal Hub · Análisis del mcp_server.py actual

Lo que hace tu mcp_server.py actual

Tu servidor actual (/home/user/agente-concursal/mcp_server.py) es un Blueprint de Flask que implementa correctamente lo básico:

  • Handshake completo: responde a initialize, tools/list, tools/call
  • JSON-RPC 2.0: el formato de respuesta es correcto
  • Una tool: consultar_agente_concursal(consulta)
  • Error handling básico: captura excepciones, devuelve código -32603

Lo que le falta (para el Quarta Legal Hub)

Problema 1: Solo una tool genérica
Una tool que hace todo es como tener un solo "Escrito General" en tus templates. Claude no puede elegir con precisión. Si tienes redactar_memorial(tipo, datos), calificar_creditos(lista_creditos), buscar_jurisprudencia(termino) como tools separadas, Claude elige la correcta según el contexto.
Problema 2: Sin Resources ni Prompts
No expone la Ley 1116 como Resource (Claude podría leerla directamente). No tiene Prompts predefinidos para los casos frecuentes de Quarta.
Problema 3: Sin autenticación
Cualquiera que sepa la URL puede llamar tu API. En Railway con datos de clientes, eso es un problema de confidencialidad grave.
