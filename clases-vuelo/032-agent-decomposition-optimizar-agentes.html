Agent Decomposition: Cómo Diagnosticar y Rediseñar un Agente que Crecio Demasiado

Construyes un agente. Funciona bien. Te piden mas funcionalidad. Agregas herramientas, expandes el system prompt, añades sub-agentes. Despues de varios ciclos, el system prompt tiene 400 lineas, el agente tiene 12 herramientas y los evals empiezan a caer. Este es el problema mas comun que el equipo de Applied AI de Anthropic ve en clientes — y en sus propios proyectos internos.

"If this is you, you're not alone — we see this type of scenario happen pretty commonly with customers, actually with ourselves included."
— Will, Applied AI Engineering, Anthropic

Esta clase cubre el workshop completo de Agent Decomposition presentado en Code with Claude London. El caso de estudio es StockPilot, un agente de gestion de inventario. Pero el diagnostico y las soluciones aplican directamente al agente concursal de Quarta.

El Agente que Crecio Demasiado: StockPilot

StockPilot empezo como un agente de inventario para un retailer mediano. Funciono bien. Con el tiempo le agregaron capacidades hasta llegar a esta arquitectura:

ARQUITECTURA "BEFORE" — PROBLEMATICA
  • 1 orquestador principal
  • System prompt de ~400 lineas
  • 12 herramientas distintas
  • 3 de esas herramientas son wrappers de sub-agentes con context windows aislados
  • Pass rate en evals: 83%
ARQUITECTURA "AFTER" — OBJETIVO
  • Orquestador con system prompt de ~50 lineas
  • Skills cargados bajo demanda
  • Tools reemplazadas por primitivas human-like
  • Sub-agentes con typed contracts
  • Pass rate en evals: objetivo: 95%+

Por que 83% no es suficiente

En un sistema de recomendacion de contenido, un 17% de error es molesto. En un agente de gestion de inventario o en un agente juridico concursal, un 17% de error significa ordenes de compra incorrectas, plazos vencidos, calificaciones de creditos equivocadas. El objetivo del workshop es hacer hill climbing sobre evals hasta llegar a una tasa de fallo operacionalmente aceptable.

Los Evals: Como Medir lo que esta Fallando

Antes de redisenar nada, necesitas medir. La suite de evals de StockPilot tiene 12 tareas en dos categorias:

Prefijo Tipo Descripcion
R Regression tasks Single-turn realistas. Evaluan si el agente da la respuesta correcta en casos normales.
F Failure mode tasks Multi-turn complejos. Evaluan si el agente maneja correctamente los casos criticos y extremos.

Los 5 tipos de graders

GraderCuando usarlo
exact_matchEl output debe ser identico a la respuesta correcta
set_matchEl output debe contener los mismos elementos (sin importar orden)
numeric_tolerance ±20%El output numerico debe estar dentro del margen aceptable
llm_judgeCuando la respuesta correcta requiere juicio semantico
efficiency (15k out-tokens)El agente llega al resultado correcto pero usando demasiados tokens

Formula de score: (PASS + 0.5 · PASS-SLOW) / 12 — un resultado correcto pero ineficiente cuenta solo la mitad.

Los 3 evals que fallan en la arquitectura "before"

EvalQue midePor que falla
F1 Daily low-stock sweep Llega al resultado correcto pero carga 395 filas de CSV al contexto → falla por eficiencia de tokens (324k tokens)
F2 Ordering bajo promotion package El sub-agente retorna "fairly confident" (prosa) en vez de un numero → breakdown de comunicacion con el orquestador
R8 Forecasting durante mes de promocion Dos politicas contradictorias en distintas partes del system prompt → usa multiplicador 1.35 en vez de 3.1x

RCA — Root Cause Analysis con Claude Code

Will corre los evals con Claude Code (Opus 4.7, esfuerzo extra_high) y le pide que diagnostique los fallos. Claude identifica 3 causas raiz:

Causa 1 — Compute-over-Context

El modelo esta haciendo trabajo que deberia hacer una herramienta. La tool list_low_stock manda 395 filas de CSV directamente al context window del modelo. En R2 eso son 32k tokens. En F1 son 324k tokens.

El modelo no deberia leer una tabla de 395 filas — deberia tener acceso a codigo que filtre esa tabla y le devuelva solo lo relevante.

SOLUCION
Dar a Claude una herramienta de bash para que escriba un Python script, lo ejecute y razone sobre los resultados. En vez de cargar el CSV, el modelo escribe sorted(items, key=lambda x: x.on_hand - x.safety)[0:5] y procesa solo los 5 mas criticos.

Causa 2 — Typed Contract Missing

El sub-agente de forecasting retorna "fairly confident" (una frase en prosa) en vez de un numero. El orquestador no puede procesar eso de forma deterministica. Sin un contrato de output explicito, cada sub-agente inventa su propio formato de respuesta.

SOLUCION
Definir un JSON schema en el SKILL.md del sub-agente que ancle el formato desde el principio. El sub-agente siempre retorna {"forecast_units": 340, "confidence": 0.87, "method": "promo_adjusted"} — nunca prosa.

Causa 3 — Policy-as-Skill Missing

Las politicas de negocio (multiplicadores de promocion, estructura de reportes semanales, templates de notificacion) estan mezcladas dentro del system prompt de 400 lineas o se re-derivan desde cero en cada llamada. Resultado: el modelo encuentra dos politicas contradictorias sobre el mismo multiplicador y usa la incorrecta.

SOLUCION
Mover cada politica a un SKILL.md separado. El orquestador carga el skill solo cuando lo necesita. Hay una sola fuente de verdad para cada politica.

El Meta-Patron

El agente "before" es un generalista con herramientas brutas. Cada fallo es un caso donde algo que deberia ser estructura fija — logica de filtro, schema de output, politica, template — esta siendo improvisado por el LLM en cada run. La descomposicion mueve cada uno de esos elementos al lugar correcto: tool (para computo), typed return (para contrato), skill (para politica y formato).

Solucion 1: Skills — Progressive Disclosure

Un Skill es informacion comprimida y composable que Claude carga bajo demanda cuando reconoce que la necesita para completar una tarea especifica.

SYSTEM PROMPT — SIEMPRE EN CONTEXTO

Informacion que Claude necesita independientemente de la tarea. Identidad del agente, herramientas disponibles, reglas de seguridad criticas, politicas que aplican a TODO.

SKILLS — CARGADOS BAJO DEMANDA

Informacion que Claude necesita SOLO para tareas especificas. Politicas de forecasting, templates de reportes, procedimientos de proveedores, formatos de notificacion.

Resultado en StockPilot: system prompt de 400 lineas → 50 lineas. La informacion de forecasting, politicas de promocion y templates de reportes pasaron a skills separados.

Formato de un SKILL.md

# forecasting-promo.md # Claude carga este skill cuando detecta que la tarea involucra # calculos de demanda durante periodos de promocion ## Politica de Forecasting en Promociones Durante meses de promocion, usar los siguientes multiplicadores: - Promocion estandar: 3.1x sobre demanda base - Flash sale (<48h): 2.4x - Temporada alta: 1.8x sobre base de temporada ## Output Contract Siempre retornar JSON con este schema exacto: { "forecast_units": <integer>, "multiplier_used": <float>, "period_type": "standard_promo | flash_sale | peak_season", "confidence": <float 0-1> }

La regla de oro para decidir: system prompt vs skill

Pregunta: "Claude necesita esta informacion aunque la tarea NO involucre este dominio?" Si la respuesta es si → system prompt. Si la respuesta es no → skill. Contaminar el context window con informacion irrelevante para la tarea actual degrada la calidad del razonamiento.

Solucion 2: Human-like Primitives

"Whenever we build agents, we lean into human-like primitives first. Imagine yourself when you show up to work — you have a computer, the ability to navigate files on a file system, search the web, or write code."
— Will, Anthropic

En vez de construir herramientas personalizadas para cada tarea de computo, empieza siempre con estas 4 primitivas:

bash

Code Execution

Escribe y ejecuta Python, bash, scripts. Procesa datos sin cargarlos al contexto.

fs

File System

Lee, escribe y navega archivos. El agente tiene acceso a su entorno.

todo

To-Do List

Tracking de tareas multi-paso. El agente mantiene estado de su propio progreso.

web

Web Search

Busqueda en tiempo real. Para datos que cambian o que no estan en el contexto.

Por que esto importa para analisis de datos

Caso concreto: tienes un CSV de 400 filas de acreedores con saldos. En vez de cargar el CSV al contexto del agente (costoso, lento, propenso a error), le das al agente acceso a bash. El agente escribe un Python de 3 lineas, lo ejecuta y te da directamente los 5 acreedores mas criticos. Misma respuesta, 95% menos tokens.

Claude Code funciona exactamente asi: es un gran agente de codigo porque esencialmente lo que Anthropic hizo fue darle a Claude acceso a una computadora.

Metodologia: Hill Climbing con Evals

Este es el proceso iterativo que Will usa durante el workshop con Claude Code como herramienta de diagnostico:

1
Corre evals — baseline. uv run evals --agent before. Tienes tu punto de partida: 83%.
2
Diagnostica fallos con Claude Code. Pide a Claude que analice los resultados, identifique patrones en los fallos y proponga root causes. Claude Code con Opus, esfuerzo extra_high.
3
Haz un cambio arquitectonico especifico. Un skill, una tool reemplazada por bash, un typed contract en un sub-agente. Un cambio a la vez para saber que mejoro que.
4
Corre evals de nuevo. uv run evals --task F1 para el eval especifico que atacaste. Verifica que mejoro sin regresar otros.
5
Repite. Siguiente fallo, siguiente cambio, siguiente verificacion. El progreso es incremental y medible.
# Comandos del workshop
uv run evals --agent before        # baseline completo
uv run evals --task F3             # eval especifico (skills)
uv run evals --task F1             # eval especifico (bash primitives)
uv run evals --task F2,R7          # multiples evals (sub-agente typing)

Sub-agentes con Typed Contracts

El fallo F2 en StockPilot es el patron de comunicacion rota entre sub-agente y orquestador mas comun. El sub-agente hace bien su trabajo pero retorna prosa en vez de estructura, y el orquestador no puede procesarla de forma deterministica.

SIN TYPED CONTRACT — FALLA
Sub-agente retorna:
"Based on historical trends
and the upcoming promotion,
I'm fairly confident we'll
need around 340 units."
CON TYPED CONTRACT — CORRECTO
Sub-agente retorna:
{
  "forecast_units": 340,
  "confidence": 0.87,
  "multiplier_used": 3.1,
  "period_type": "standard_promo"
}

La regla: cada sub-agente necesita un SKILL.md con el JSON schema de su output antes de escribir una sola linea del prompt del sub-agente. El contrato define la interfaz entre agentes. Sin el, el orquestador tiene que interpretar texto libre, lo que produce comportamiento impredecible.

Aplicacion a Quarta: El Agente Concursal

Diagnostico de Quarta con el mismo framework

El agente concursal de Quarta tiene el mismo patron de crecimiento organico que StockPilot. Aplica el mismo RCA:

Compute-over-Context en Quarta

Si el agente carga el texto completo de expedientes, resoluciones o tablas de acreedores al contexto para analizarlos, esta usando el patron incorrecto. La solucion: bash tool que ejecute un script Python para filtrar, calcular y retornar solo los datos relevantes.

Ejemplo: en vez de cargar 200 paginas de un expediente, el agente escribe un script que extrae solo las secciones con los plazos de impugnacion y los montos de credito.

Policy-as-Skill en Quarta

Las reglas del proceso concursal colombiano — plazos de la Ley 1116, criterios de calificacion de creditos, jerarquia de acreedores — no deben estar hardcodeadas en el system prompt mezcladas con otras instrucciones. Cada dominio legal va a un skill separado:

  • ley-1116-plazos.md — plazos de impugnacion, terminos de publicacion, vencimientos de inventario
  • calificacion-creditos.md — criterios de prelacion, clases de creditos, politica de gradacion
  • reporte-semanal-promotor.md — template de reporte para el promotor del proceso

Typed Contracts en Quarta

Si el agente de analisis de creditos retorna un parrafo explicativo en vez de un JSON con los campos exactos (monto, clase, acreedor, estado), el agente de generacion de documentos no puede procesarlo de forma deterministica. Define el schema antes de construir el sub-agente.

Evals para Quarta

El agente concursal necesita su propia suite de evals con los mismos tipos de graders:

  • exact_match: el plazo calculado coincide con la fecha correcta segun Ley 1116
  • set_match: el listado de acreedores de primera clase incluye exactamente los creditos correctos
  • llm_judge: el memorial de objeciones tiene los argumentos juridicos correctos
  • efficiency: el agente completa el analisis sin exceder 15k tokens de salida

Comprobacion de Conocimiento

1. El eval F1 de StockPilot falla por "eficiencia de tokens" — el agente llega al resultado correcto pero usa 324k tokens. Cual es la causa raiz segun el RCA?

Correcto. Causa raiz 1 — Compute-over-Context: la tool manda datos brutos al contexto cuando deberia calcular y retornar solo el resultado. La solucion es dar al agente una bash tool para que escriba un Python script que filtre los datos.
Incorrecto. La causa raiz es Compute-over-Context: list_low_stock manda 395 filas de CSV al contexto del modelo (324k tokens). El modelo no deberia leer tablas — deberia tener acceso a herramientas de computo que filtren los datos y retornen solo lo relevante.

2. Cual es la diferencia critica entre informacion que va al system prompt vs informacion que va a un skill?

Correcto. El principio de progressive disclosure: system prompt = informacion siempre necesaria. Skill = informacion cargada bajo demanda cuando la tarea especifica la requiere. Contaminar el contexto con informacion irrelevante degrada el razonamiento.
Incorrecto. La distincion es: system prompt para informacion siempre necesaria independientemente de la tarea. Skills para informacion relevante SOLO en tareas especificas. Los skills implementan progressive disclosure — el contexto solo contiene lo que la tarea actual necesita.

3. El eval R8 falla porque el agente usa multiplicador 1.35 en vez de 3.1x durante un mes de promocion. Cual es la causa raiz?

Correcto. Causa raiz 3 — Policy-as-Skill Missing: cuando la politica de multiplicadores de promocion vive dispersa en un system prompt de 400 lineas, pueden existir dos versiones contradictorias. El modelo encuentra ambas y usa la incorrecta. La solucion es mover cada politica a un skill separado.
Incorrecto. La causa raiz es Policy-as-Skill Missing. El system prompt de 400 lineas tiene dos definiciones contradictorias del multiplicador de promocion. El modelo las encuentra ambas y usa la incorrecta. La solucion: un skill dedicado para politicas de forecasting, con una sola fuente de verdad.

4. Segun el principio de "human-like primitives", cual es la forma correcta de analizar un CSV de 400 filas con un agente?

Correcto. La primitiva de code execution (bash/Python) es la solucion correcta. El agente escribe el codigo de filtrado, lo ejecuta y procesa solo los resultados relevantes. Mismo resultado, 95% menos tokens que cargar el CSV completo.
Incorrecto. La solucion de human-like primitives es darle al agente acceso a bash para ejecutar codigo. El agente escribe un script Python que filtre el CSV y retorna solo los datos relevantes. No se carga el CSV al contexto — se computa sobre los datos.

5. En la metodologia de hill climbing con evals, cual es el orden correcto de pasos?

Correcto. Hill climbing es iterativo e incremental: baseline → diagnostico → UN cambio → verificacion → siguiente iteracion. Hacer todos los cambios a la vez hace imposible saber que mejoro que y que introdujo regresiones.
Incorrecto. El hill climbing correcto es: baseline → diagnosticar → UN cambio especifico → verificar → repetir. La clave es un cambio a la vez. Si haces varios cambios simultaneamente, no puedes saber cual mejoro el score y cual introdujo una regresion.
