Clase 003 · Bloque 0: Fundamentos de Calibración · Repo: agente-concursal · ~8 min

RAG por dentro — los 3 pasos y dónde falla cada uno

Calibración · Ya construiste RAG. Ahora lo diseccionas.
Concepto

RAG (Retrieval-Augmented Generation) no es una tecnología misteriosa — son tres pasos concretos ejecutados en orden. Tu agente concursal ya los hace. Esta clase los nombra con precisión para que puedas diagnosticar problemas.

1
Embed
Convertir la pregunta del usuario en un vector numérico usando un modelo de embedding
2
Retrieve
Buscar en ChromaDB los fragmentos con vectores más cercanos al de la pregunta
3
Augment
Inyectar esos fragmentos en el prompt de Claude como "contexto" antes de responder
Como preparar un alegato de conclusión: buscar jurisprudencia relevante (retrieve = ir al archivo y traer los expedientes correctos), leerla y subrayar lo útil (augment = ese texto se le pasa a Claude), redactar el alegato (generate = Claude produce la respuesta). Si el archivo está mal indexado, el alegato sale mal — independientemente de qué tan bueno sea Claude.
Flujo completo — tu agente concursal actual
ABOGADO: "¿Cuál es el término para objetar créditos?" │ ▼ ┌─────────────────────────────────────────────────┐ │ PASO 1: EMBED (agente.py, línea ~50) │ │ pregunta → DefaultEmbeddingFunction() │ │ → vector [0.23, -0.87, 0.45, ...] (384 dims) │ └──────────────────────┬──────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────┐ │ PASO 2: RETRIEVE (agente.py) │ │ _collection.query( │ │ query_texts=[pregunta], │ │ n_results=7 ← N_RESULTADOS = 7 │ │ ) │ │ → 7 fragmentos de la Ley 1116 más cercanos │ └──────────────────────┬──────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────┐ │ PASO 3: AUGMENT (construir el prompt) │ │ contexto = "\n\n".join(fragmentos) │ │ │ │ prompt_final = f""" │ │ CONTEXTO NORMATIVO: │ │ {contexto} │ │ │ │ PREGUNTA: {pregunta} │ │ """ │ └──────────────────────┬──────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────┐ │ GENERATE: Claude (claude-opus-4-5) │ │ Recibe: system_prompt + contexto + pregunta │ │ Produce: respuesta legal fundamentada │ └─────────────────────────────────────────────────┘
Dónde puede fallar cada paso
Falla en EMBED: el modelo de embedding no entiende bien el español legal. "Acreencia" puede no quedar cerca de "crédito reconocido" en el espacio vectorial. Solución: modelos de embedding multilingües o especializados (clase 016).
Falla en RETRIEVE: los fragmentos traídos no contienen la respuesta, aunque exista en la base. Causas: chunk size muy pequeño o muy grande, n_results insuficiente, o pregunta muy diferente en vocabulario a los documentos. Solución: mejor chunking, query expansion, reranking (clase 016).
Falla en AUGMENT: los 7 fragmentos son relevantes pero Claude no los usa bien — porque el contexto está mal formateado, está al final del prompt, o el system prompt no le indica cómo usarlos. Solución: estructurar el contexto con XML tags (clase 006).
Regla de diagnóstico: cuando el agente da una respuesta mala, primero imprime los fragmentos recuperados (print(fuentes)). Si los fragmentos son relevantes → falla en Augment/Generate. Si los fragmentos son irrelevantes → falla en Embed/Retrieve.
Quarta — parámetros actuales de tu RAG

En agente.py los parámetros clave son: CHUNK_SIZE = 900 caracteres, CHUNK_OVERLAP = 180, N_RESULTADOS = 7. Esto significa:

  • Cada fragmento de la Ley 1116 tiene ~900 caracteres (~150 palabras)
  • Hay 180 caracteres de solapamiento entre fragmentos consecutivos (evita cortar en mitad de artículo)
  • Claude recibe los 7 fragmentos más relevantes como contexto en cada consulta
  • 7 × 900 = ~6,300 caracteres de contexto = ~1,575 tokens solo de contexto normativo

En la clase 016 evaluarás si estos números son óptimos para consultas de derecho concursal colombiano, o si conviene aumentar N_RESULTADOS para preguntas complejas sobre graduación de créditos (que involucran múltiples artículos).
