Evaluación de prompts — cómo saber si tu agente funciona bien

Por qué "lo pruebo y veo" no escala — y cómo construir evals para escritos legales
Concepto

Un eval (evaluation) es un conjunto de casos de prueba con respuestas esperadas que te permite medir objetivamente si un prompt produce outputs de calidad. Sin evals, cada cambio al system prompt es un experimento ciego.

Para agentes legales, la evaluación importa más que en otros dominios porque un error de Claude (artículo equivocado, clase de crédito incorrecta) puede tener consecuencias reales en el proceso. Los evals son tu red de seguridad.

El patrón más poderoso para aplicaciones como Quarta: usar al propio Claude como juez de las respuestas (LLM-as-judge). Claude evalúa si la respuesta del agente cumple ciertos criterios — más rápido y escalable que revisión manual.

Cómo funciona — pipeline de eval
PIPELINE DE EVAL PARA AGENTE CONCURSAL: ───────────────────────────────────────── 1. DATASET DE CASOS DE PRUEBA ┌─────────────────────────────────────────────┐ │ input: pregunta legal │ │ expected: respuesta esperada (o criterios) │ │ metadata: tipo_consulta, norma_relevante │ └─────────────────────────────────────────────┘ 2. EJECUCIÓN input → [agente concursal] → respuesta_generada 3. EVALUACIÓN (LLM-as-judge) {respuesta_generada + criterios} → [Claude evaluador] → score + feedback 4. MÉTRICAS AGREGADAS ✓ Precisión normativa: ¿cita artículos correctos? ✓ Formato: ¿estructura forense correcta? ✓ Confidencialidad: ¿usó placeholders? ✓ Completitud: ¿respondió todos los aspectos de la pregunta? ✓ Tono: ¿lenguaje forense colombiano? 5. REGRESIÓN Comparar scores entre versión A y versión B del prompt → Solo actualizar si B ≥ A en todas las métricas críticas

Código — LLM-as-judge para outputs legales
import anthropic
import json
from dataclasses import dataclass

client = anthropic.Anthropic()

@dataclass
class CasoPrueba:
    id: str
    input: str
    expected_criteria: list[str]  # qué debe cumplir la respuesta
    tipo: str  # "normativa", "memorial", "clasificacion", "guardrail"

JUEZ_SYSTEM_PROMPT = """
Eres un juez evaluador de respuestas de un agente de derecho concursal colombiano.
Evalúa si la respuesta cumple los criterios especificados.
Devuelve un JSON con: {"score": 0-100, "criterios_cumplidos": [], "criterios_fallidos": [], "feedback": ""}
"""

def evaluar_respuesta(respuesta: str, criterios: list[str]) -> dict:
    """Claude evalúa si la respuesta del agente cumple los criterios."""
    criterios_str = "\n".join([f"- {c}" for c in criterios])
    result = client.messages.create(
        model="claude-haiku-4-5",  # modelo más barato para evaluar
        max_tokens=512,
        system=JUEZ_SYSTEM_PROMPT,
        messages=[{
            "role": "user",
            "content": f"""<respuesta_agente>
{respuesta}
</respuesta_agente>

<criterios_a_evaluar>
{criterios_str}
</criterios_a_evaluar>

Evalúa y devuelve JSON."""
        }]
    )
    try:
        return json.loads(result.content[0].text)
    except:
        return {"score": 0, "feedback": "Error parsing judge response"}

def correr_eval_suite(agente_fn, casos: list[CasoPrueba]):
    """Corre todos los casos de prueba y reporta resultados."""
    resultados = []
    for caso in casos:
        respuesta = agente_fn(caso.input)
        evaluacion = evaluar_respuesta(respuesta, caso.expected_criteria)
        resultados.append({
            "id": caso.id,
            "tipo": caso.tipo,
            "score": evaluacion["score"],
            "feedback": evaluacion.get("feedback", "")
        })
        print(f"[{caso.id}] Score: {evaluacion['score']}/100")
    score_promedio = sum(r["score"] for r in resultados) / len(resultados)
    print(f"\nScore promedio: {score_promedio:.1f}/100")
    return resultados
Quiz — 3 preguntas
Pregunta 1 / 3
Para el eval del agente concursal, decides usar claude-haiku-4-5 como juez en lugar de claude-opus-4-5. ¿Cuándo esta decisión tiene sentido y cuándo no?
Tiene sentido para criterios simples y objetivos (¿usó placeholder?, ¿mencionó el artículo?, ¿tiene sección de Peticiones?). Haiku es 10× más barato y suficiente para verificar criterios binarios.

No tiene sentido para criterios subjetivos complejos (¿el razonamiento jurídico es correcto?, ¿el tono es forense colombiano?, ¿la graduación de créditos es legalmente válida?). Para estos, necesitas Opus o Sonnet — o mejor aún, revisión manual de un abogado para los casos de alto riesgo.
Pregunta 2 / 3
Mejoras el system prompt del agente concursal (versión A → versión B). Los evals muestran que B sube de 75 a 90 en "precisión normativa" pero baja de 85 a 70 en "formato_forense". ¿Actualizas a la versión B?
No actualizas todavía. El sistema de evals sirve precisamente para detectar regresiones como esta. La caída en formato_forense es una señal de que el cambio resolvió un problema pero creó otro. La solución correcta: investigar por qué B deterioró el formato (¿eliminaste una instrucción de formato? ¿el nuevo texto de las capacidades cambió la identidad?), corregirlo, y crear una versión C que suba ambas métricas. Solo actualizas cuando todas las métricas críticas son iguales o mejores.
Pregunta 3 / 3
El Caso 009 prueba "no alucinación de artículo" — le pides al agente que explique un artículo que no existe. ¿Por qué este caso de prueba es tan importante para un agente legal y qué comportamiento específico buscas?
Es crítico porque los LLMs pueden inventar artículos con total confianza. Un abogado que presenta un memorial citando "Art. 999 de la Ley 1116" a un juez de Supersociedades pierde credibilidad inmediatamente — y potencialmente el proceso.

El comportamiento que buscas: Claude debe reconocer que ese artículo no existe en lugar de inventar contenido plausible. Esto requiere que el system prompt tenga explícitamente la regla: "Si un artículo no está en tu contexto, escribe [VERIFICAR ART. X] en lugar de inventarlo". El eval te confirma que el guardrail está funcionando.
